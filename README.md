# LABBOR Studio

SaaS-платформа для зуботехнических лабораторий: заказы, техники, зарплаты, аналитика.
Мультитенантная система — одна инсталляция обслуживает много независимых лабораторий,
каждая со своей подпиской и своим набором сотрудников.

Figma: https://www.figma.com/design/tMLOjscar2FKLEyH9AIkLw/%D0%97%D1%83%D0%B1%D0%BE%D1%82%D0%B5%D1%85%D0%BD%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B0%D1%8F-%D0%BB%D0%B0%D0%B1%D0%BE%D1%80%D0%B0%D1%82%D0%BE%D1%80%D0%B8%D1%8F?node-id=0-1&t=3A7H03TB9V53gzjx-1

## Стек

- **Backend** — NestJS 11 + PostgreSQL + Prisma ORM (`backend/laba-backend`)
- **Frontend** — Next.js 16 (App Router) + Tailwind v4, дизайн-система LABBOR (`frontend`)
- **Auth** — JWT (access + refresh), сессии в БД, роли в контексте лабы

## Быстрый старт

Нужен только Docker.

```bash
cp .env.example .env   # опционально: свои секреты/пароли
docker compose up --build
```

Поднимутся три контейнера:

| Сервис | Порт | Что это |
|---|---|---|
| `postgres` | 5432 | база данных |
| `backend` | 3000 | API (`/api`), Swagger-документация (`/docs`) |
| `frontend` | 3001 | веб-интерфейс |

Миграции применяются автоматически при старте `backend` (`prisma migrate deploy`).

### Первый запуск

В системе изначально нет ни одного пользователя. Открой **http://localhost:3001** —
не найдя платформенного администратора, приложение само перекинет на `/setup`, где
нужно один раз создать учётку суперадмина (email, пароль, имя/фамилия). Это единственный
способ инициализации — сработает ровно один раз, повторно эндпоинт закрывается сам
(без seed-скриптов и ручных SQL-вставок).

Дальше суперадмин работает через API/Swagger (`http://localhost:3000/docs`), потому что
в веб-интерфейсе пока нет собственного личного кабинета платформы — только рабочий
дашборд лаборатории (см. «Что дальше» ниже).

## Логика системы

### Сущности

- **User** — аккаунт (email + пароль). Один и тот же email может состоять сразу в
  нескольких лабораториях.
- **Lab** (лаборатория) — единица тенанта. Все данные лабы изолированы от других лаб.
- **LabMembership** — связь пользователь ↔ лаба с ролью и статусом:
  - роли: `OWNER` (владелец), `ADMIN` (администратор), `TECHNICIAN` (техник);
  - статус `ACTIVE` / `BLOCKED` — владелец/админ может заблокировать сотрудника без
    удаления аккаунта, сессии при этом отзываются мгновенно.
- **Subscription** — подписка, привязанная к конкретной лабе (не к владельцу). Статусы:
  `TRIALING`, `ACTIVE`, `PAST_DUE`, `EXPIRED`, `CANCELED`.
- **Session** — запись о выданном refresh-токене. Хранение в БД позволяет точечно или
  массово отзывать доступ (логаут, блокировка сотрудника, истечение подписки).

### Кто как попадает в систему

Самостоятельной регистрации нет — только приглашения:

1. **Платформенный администратор** создаётся один раз через `/setup` (см. выше).
2. Суперадмин создаёт лабораторию и владельца: `POST /api/labs` — заводит лабу,
   пробную подписку (`TRIALING`) и приглашение на email владельца.
3. Владелец переходит по ссылке-приглашению (`/invites/:token/accept` на фронте),
   задаёт себе пароль — и сразу залогинен.
4. Владелец приглашает администраторов и техников в свою лабу:
   `POST /api/labs/:labId/invites` (кто кого может звать — см. ниже). Приглашённый
   принимает инвайт по такой же публичной странице.

Иерархия приглашений и блокировок: `OWNER` может звать/блокировать `ADMIN` и
`TECHNICIAN`; `ADMIN` — только `TECHNICIAN`.

### Подписка и доступ

Подписка проверяется в двух местах:

- **При входе и при принятии приглашения** — если подписка лабы не `TRIALING`/`ACTIVE`,
  логин и регистрация новых сотрудников блокируются сразу.
- **Фоновой задачей** (каждые 5 минут) — просроченные подписки помечаются `EXPIRED`, и
  все активные сессии сотрудников этой лабы отзываются принудительно (мгновенный логаут
  на всех устройствах).

### Токены и сессии

Access-токен (JWT, живёт 15 минут по умолчанию) несёт `userId`, `labId`, роль и id
сессии. Refresh-токен (30 дней) хранится в БД в виде хеша и ротируется на каждый
`POST /api/public/auth/refresh`. У владельца с несколькими лабами токен всегда привязан
к одной конкретной лабе — переключение между ними: `POST /api/auth/switch-lab`.

Изоляция между лабами обеспечивается тем, что `labId` зашит в токене и на каждом
запросе сверяется с ресурсом, а не приходит от клиента бесконтрольно.

## Структура репозитория

```
backend/laba-backend/   NestJS API (см. Swagger /docs — там описан каждый эндпоинт)
frontend/               Next.js приложение
  src/app/(dashboard)/    рабочий дашборд лабы (рейл + топбар), пока на моках
  src/app/setup/          публичная страница первичной инициализации
  src/app/invites/        публичная страница принятия приглашений
docker-compose.yml       postgres + backend + frontend одной командой
```

## Переменные окружения

Все опубликованы с рабочими дефолтами в `docker-compose.yml` — для локального запуска
`.env` не обязателен. Полный список — в `.env.example` (корень репозитория) и
`backend/laba-backend/.env.example` (для запуска бэкенда без докера). Для прода
обязательно смени `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` и пароль Postgres.

## Разработка без Docker

```bash
docker compose up -d postgres        # только база
cd backend/laba-backend && npm install && npm run start:dev
cd frontend && npm install && npm run dev
```

Подробности по бэкенду (миграции, генерация Prisma-клиента, нюансы Prisma 7) — в
`backend/laba-backend/README.md` (если понадобится — там же история решённых проблем
с локальным окружением). Конвенции фронтенда (дизайн-система, структура компонентов,
правила стилизации) — в `frontend/AGENTS.md` и корневом `DESIGN_SYSTEM.md`.

## Что дальше

Дашборд лаборатории (`(dashboard)` в фронтенде) пока работает на моковых данных — это
следующий шаг: завести полноценный логин, подключить реальные API-запросы вместо
`src/lib/mocks/*` и личный кабинет платформенного администратора для управления лабами
из UI, а не только через Swagger.
